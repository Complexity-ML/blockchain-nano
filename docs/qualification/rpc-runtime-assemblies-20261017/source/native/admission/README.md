# Admission prospective de produits Native

Source seule, sans CLI. Root charge ce module public par son procédé FD/SHA habituel, puis appelle `install(m)`. Le module injecté conserve l’API `m.admit_products(paths, name, executable=False)`. Aucun ancien helper ni résultat d’essai n’est modifié.

Le helper s’appuie sur les fonctions déjà retenues de `m` : `material` (fichier physique, FD/path neuf champs et SHA), `digest`, `output`, `fence`, `save`, `need`, ainsi que `AUTH`, `HELD`, `PRODUCTS`, `NEW` et `DEADLINE`. Pour les objets du refus Native02, Root doit d’abord renseigner `m.NEW[path] = {sha256, bytes}` avec les pins connus du producteur, et joindre séparément la preuve M=MD retenue. Le helper ne prouve ni compilation ni M=MD. Pour les futurs nouveaux liens, il conserve le comportement historique de `output`, qui amorce le premier pin d’octets s’il est absent ; un pin NEW déjà présent n’est jamais remplacé.

Chaque observation relit les fichiers par `material`, exige SHA et taille NEW exacts, UID501 et nlink1. Un exécutable nouvellement produit est mis en0500 avant l’observation ; aucun fichier déjà présent dans AUTH/HELD/PRODUCTS ne peut être chmodé. Toute identité sélectionnée déjà retenue dans ces tables doit rester exactement égale, sans modification de son ancienne ligne. Le helper n’énumère pas toute l’autorité AUTH historique. Les fences actives existantes restent exécutées.

Avant toute première inscription dans PRODUCTS, les lignes neuf champs+SHA de tous les produits doivent être égales pendant au moins trois observations consécutives séparées d’au moins deux secondes. Un changement de métadonnées recommence seulement cette série ; un changement d’octets, un échec FD/path ou une ancienne identité différente refuse immédiatement. La fenêtre prospective est de30s au maximum, bornée aussi par DEADLINE. Les contrôles de délai se font entre les I/O synchrones et avant l’inscription : ce n’est pas un minuteur interrompant un appel noyau bloqué. La fence finale et l’écriture des diagnostics peuvent suivre cette fenêtre, sous les bornes du contrôleur hôte. Après inscription, une erreur ne retire ni ne réinitialise cette nouvelle autorité.

Le fichier privé `NAME-product-first-observations.private.json` est demandé dans le finally à `m.save`, dont la publication exclusive habituelle reste inchangée. Il porte le format distinct `nano-native-prospective-product-admission-v1`, les pins, toutes les observations (y compris partielles), la série stable, le statut d’inscription et la première erreur. Un échec de diagnostic ne remplace jamais une erreur antérieure ; s’il n’existait aucune erreur, l’échec d’écriture est propagé. Les appels invalides sans nom sûr ne créent pas de fichier. L’arrêt brutal du processus ou une panne de stockage ne garantissent pas l’écriture du diagnostic.

Aucun contrôleur, test, compilateur ou programme du projet n’a été exécuté par l’auteur. L’AST a seulement été analysé. Aucun SDK, entrée privée ou artefact n’a été lu. L’échec Native02 reste conservé ; sa cause exacte de variation de métadonnées n’est pas revendiquée. Aucun résultat Native476, runtime, duties, campagne, SDK global ou production n’est obtenu par cette routine.
