## Déroulement, clôture et sorties

L’hôte réemploie les helpers f28 et la structure Docker/fences de host3be. Il crée uniquement une sortie neuve disjointe et un conteneur SDK existant fd9, UID/GID1000, CPU2/RAM3GiB/pids128/tmpfs1536MiB, root/input RO, sortie RW, network none, sans image build/pull. Deux sources sont à stager : cet hôte et le worker V2 original. Les métadonnées et copies publiques Root sont des entrées contrôlées, sans transfert de capsule/clé/journal.

Les huit exécutables ont des bind mounts individuels RO. Leur admission guest prospective exige leurs SHA/taille originaux à chaque observation, trois tables GNU stat/SHA identiques sur au moins deux secondes sous trente secondes. Cette admission concerne les métadonnées d’un nouveau montage guest ; elle ne réadmet jamais leurs lignes originales hôte. La table guest est ensuite strictement comparée après chaque CLI et avant cleanup. Elle ne prouve pas une identité FD guest ou une closure globale de loader.

Aucun résultat de durée n’est affirmé par l’auteur.

Toute première erreur est conservée. Les diagnostics, vérifications finales et cleanup ne peuvent transformer le précédent FAILED en PASS.
