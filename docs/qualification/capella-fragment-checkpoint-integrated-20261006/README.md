# Migration et restauration de checkpoints Capella fragmentés

Départ main `40dbeb74169daff352a93e6ae190ea9490e3a620`. Le réacteur publie un manifeste canonique et des fragments immuables dans les batches synchrones du primaire et du témoin séparé. La restauration authentifie les fragments puis exécute la validation complète Capella existante. Les anciens checkpoints restent lisibles. La migration explicite conserve le graphe logique et l’identité réseau ; le format fragmenté reste utilisé aux publications suivantes. Le runtime expose `fragmentCheckpointMigration` (booléen, false par défaut), avant le démarrage de l’horloge et du signataire.

## Qualification exacte

Images et volumes existants réutilisés, aucune image reconstruite, aucun nœud WAN lancé. Trois unités modifiées (chain_beacon, consensus_capella_reactor, consensus_capella_runtime) et la fixture compilées par architecture, puis archive incrémentale issue du stockage `5fff149c`. Anciennes signatures de publication conservées ; aucune modification de layout des classes. **Ce n’est pas un build propre de release ni une nouvelle candidate runtime installée.** Les 1606 fichiers figés correspondent au worktree et au VPS ; archives parentes vérifiées inchangées. Commandes, dépendances et hashes exécutables conservés.

ARM64 : initial 47715/1, chemin `/work/tests/fixtures` absent ; même binaire, montage corrigé, 93199/0. AMD64 : initial 58925/1, même erreur ; montage corrigé, 13334/1, scénario nouveau + owner-witness + configured-runtime passent, automatic-recovery échoue sur `Too many open files`. Seul automatic-recovery rejoué, même binaire avec nofile=65536, 76149/0. Tous les logs des échecs restent conservés ; les controller-exit initiaux ne sont pas réécrits comme réussites.

Sur les deux architectures, nouveau scénario Capella valide : annulation avant migration sans changement, migration idempotente, token suivant exact, graphe et identité inchangés, manifeste/fragments primaire-témoin identiques, récupération depuis un primaire indépendant resté au token précédent grâce au témoin et à l’engagement externe, admission d’un enfant signé via le chemin ordinaire, archive signée conservée, redémarrages primaire/témoin, trois refus de fragments supprimés ou altérés (primaire supprimé/altéré, témoin supprimé). Le journal créé séparément ne change pas ; ce scénario ne prétend pas qualifier un historique anti-double-signature complet. La disposition primaire précédent est construite indépendamment, pas obtenue par panne physique.

Les trois régressions existantes passent : owner-witness (trois dispositions), configured-runtime et automatic-recovery (64 clés, 16 blocs, restauration signataire/témoin, arrêt workers). Leur configuration ne demande pas la migration : **le démarrage réel via le flag true n’est pas qualifié par ces régressions**. Nouveau CTest `consensus_capella_fragment_checkpoint_migration` enregistré, exécution directe du mode correspondant ici, pas campagne CTest globale.
