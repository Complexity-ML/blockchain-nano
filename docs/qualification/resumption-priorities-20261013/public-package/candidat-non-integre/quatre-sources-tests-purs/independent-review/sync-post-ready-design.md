# Plan étroit de disponibilité sync après préparation prête

Ce document est un design statique demandé par le parent. Aucun changement, test ou build supplémentaire n’est exécuté. Le lot candidat pure11cases ne résout pas encore ce chemin.

Le cas manquant est `CapellaDutyPreparation.ready()==true` au slot63/E7, alors que `sync_state()` avance la copie vers slot64/E8 et refuse la sélection future vide. Ce refus est distinct de la préparation locale principale : il ne doit pas faire passer `projection_blocked_` à true ni masquer une proposition/attestation valide au slot63.

| Site | Proposition | Comportement conservé |
|---|---|---|
| `consensus_capella_duty.hpp/.cpp` : strict `sync_state` | Ajouter `try_sync_state(trials,checkpoint) -> optional<CapellaSlotState>` autour de la projection pure strictement locale, sur une copie ; catch uniquement `EmptyAltairSyncActiveSet` réel. Wrapper checkpoint marque toute exception du callback et la propage, même du même type. Ready/budgets/overflow restent des erreurs. | `sync_state` strict reste disponible, aucune modification de `projection_blocked_`, `ready()` ou proposition/attestation ; aucun état inventé, aucune signature. |
| `consensus_capella_sync_signing.cpp:8–22` et ses deux consumers27/46 | API privée `sync_signing_context_locked -> const SyncSigningContext*`. Utiliser try uniquement pour l’avancement local ; null retourne nullptr avant construction/publication du cache. `current_sync_members` rend `{}`, `sync_current` rend `nullopt` avant `disk_.fork_checkpoint`, `journal.ready/sign`, provider et admission. | Aucun nouveau catch global ni conversion artificielle en Stale pour ce cas ; callbacks/ressources/fautes non typées gardent leur propagation. Les deux consumers détiennent déjà mutex_, donc durée de vie du pointeur vers optional cache protégée. L’ancien cas de préparation principale incomplète peut garder sa Stale existante. |
| `consensus_capella_local_body.cpp:22–35` : admission sync entrante | Garder `sync_state` strict et le fallback `prepare_capella_slots` strict. Ne pas appeler try, ne pas retourner un faux contexte/vote à partir de null. | Vérification BLS, SSZ, membership, timing, source de confiance et refus des messages restent inchangés ; pas de traitement indulgent côté réseau. |

La private API a exactement deux callers actuels, tous deux sous mutex_. Ne pas retourner un pointeur vers une variable locale. Le cache positif conserve ses bindings `(slot,parent)` ; un null ne publie pas un contexte partiel. La correction minimale n’a pas besoin d’un nouveau cache permanent. Si un coût répétitif réellement observé exige plus tard une memo, la limiter à un résultat d’indisponibilité `(immutable parent, profile, signed slot)` de sync seulement, sans éteindre les autres duties.

Contre-exemple nouveau recommandé, sans rejouer la reproduction E8 principale : même contexte public synthétique exitE8 ; target63 qui se prépare entièrement et conserve proposer/contextes d’attestation accessibles. Strict sync64 doit encore jeter le type ; try doit retourner null et préserver exactement le frame prêt et ses états/proposals/attestation contexts. Vérifier callback même type au début et au milieu, resource error, readyfalse/zero budget ; pas de cache global. Une nouvelle tête synthétique à domaine/profil identique où un membre reste actif doit permettre un contexte sync positif recomputé. Ce test pur ne prouve pas admission de tête réelle.

L’intégration distincte avec vrais Reactor/journaux/providers doit confirmer : le poll qui a produit une proposition/attestation63 conserve ses compteurs/réservations et reste sain lorsqu’aucune sync64 n’est disponible ; zéro nouveau provider/journal write pour sync indisponible ; callback/provider/journal/admission error non pertinente demeure visible et fatale selon règles existantes ; nouveau parent réellement authentifié rétablit les sync duties. Les clés/histoire anciennes ne sont jamais réinitialisées. Runtime, sync post-ready, variantes de replay et production restent ouverts avant ce lot de qualification.
