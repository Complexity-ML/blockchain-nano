# Real loopback HTTP and exec handoff — source proposal

This new Linux-only test target executes the existing, separately qualified `nano-capella-lifecycle-submit` child. It does not include that helper or invoke its26 callback cases. A real ephemeral TCP listener is bound only to127.0.0.1; Docker `--network=none` still supplies the loopback namespace. The test launches the actual shim with `posix_spawn`, the same bounded argv shape and supervisor-context environment names used by `src/node.cpp`. The parent is a synthetic test supervisor, not `nano`: no full supervisor, signing-key exclusion, genuine consensus admission, active P2P network or complete lifecycle claim follows from this test.

The positive case sends real HTTP responses in13-byte server writes, including one pending receipt followed by completion and Forget. A private plan pins the synthetic manifest/action and an independently copied executable named `nano-p2p`. The latter is a copy of this test binary, not the real network daemon. Only when execv reaches that copy does its separate daemon mode run. It checks every original argument, the private synthetic token, the unchanged parent and absence of both submission-control variables. A private report binds its PID to the actual child PID returned by posix_spawn, proving replacement of that process rather than a reported intention to exec. The parent also verifies exact accepted-result8/job5 fields, canonical action SHA, receipt/event binding, and absence of token, session, private path and response sentinel in child logs.

Four negative cases use fresh separate controls. A dropped Submit response yields one real Submit and an empty reserved result; replaying the same plan must fail before any additional HTTP request and leave that exact reservation intact. This remains UNKNOWN outcome, not a claim that an operation was rejected or accepted. Duplicate Content-Length headers cause a fixed redacted refusal before Submit. A server that receives status but never replies must trigger the shim's real10-second total deadline without an external kill. The final case delivers SIGTERM while the child is blocked on real HTTP and waits for that exact child to close; it does not claim that the real Nano supervisor has been exercised. Parent-death behavior is not added here. On exceptions, a server stop/join guard runs while its referenced fixture is still alive; child cleanup precedes that guard. Forced cleanup is not a passing child outcome. Test refusals add only a fixed literal stage (setup, positive, lost, malformed, deadline, cancel or summary), never exception contents.

Expected totals are five groups/six rows, six shim process starts, eleven HTTP requests, one actual controlled exec handoff and five refused or terminated children. The test's cooperative whole-run limit is45s; ROOT must retain the external60s timeout. Self and waited-child peak RSS must each stay at most128MiB; these are reported separately and are not a sum-of-process-peaks claim. The candidate and test software are each read through stable owned regular single-link FDs before and after; their full nine fields and SHA/size must remain exact. All actual input fixtures also retain strict full9/SHA fences. Private fixtures and logs remain under a new owner-only OS temporary root for ROOT diagnostics; no old file or directory is deleted or normalized.

The CMake overlay is based exactly on the public current CMake03f1aeeb/172929 bytes at ROOT-reported mainb5. It adds only one Linux conditional test target, its compile-time `NANO_TEST_SUBMISSION_SHIM` path, the dependency on the unchanged real child and a new60s CTest. Existing target flags, the core and all Phase1 sources remain byte-unchanged. A ROOT thin build may instead define the macro as an absolute path such as `/qualified-submit/nano-capella-lifecycle-submit` in a directory-bound read-only qualified build. Do not single-file bind that public software if it changes the visible owner: the test keeps the same UID checks. Normal CLI has no arguments. The controlled-daemon branch is selected only by its copied executable's basename `nano-p2p`.

The synthetic operation wire is deliberately opaque and unsigned. The fake HTTP peer validates its exact shape and commitment but is not a cryptographic admission oracle. No key, signer, DB, capsule or prior campaign asset is used. No agent executed this program, a compiler, old tests, Docker, SSH or Git, and no R/L file was changed. Runtime qualification remains pending ROOT compilation and execution.

Recovery owns the separate feasibility study of a genuine `nano` supervisor path. The minimal candidate is an independently authorized fresh domain, a real stopped P/W pair and externally pinned action request, followed by an immediate proposer-slashing action for a distinct already-active initial validator and one managed restart through the shim to the real pinned P2P daemon. The fresh action policy does not apply voluntary-exit tenure to proposer slashing; the64/256 profile remains unchanged. That path still needs genuine stopped receipts, key authority, ownership and cleanup proof. It is not implemented or qualified by the component test here, and no multi-hour lifecycle or private VPS transfer is authorized by this source package.
