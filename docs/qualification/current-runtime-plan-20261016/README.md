# Proposition concrète de campagne fullLifecycle à trois owners

Ce dossier est un **brouillon source non exécutable**, sans seed, clé, ledger, domaine ou runtime créé. Les 21 programmes et trois Core ont des identités publiques exactes. Root a depuis émis séparément les trois admissions de code à treize champs ; leurs pins et chemins réels sont liés par `full-lifecycle.spec.proposed.json`. Ces admissions de code ne donnent aucune autorisation de campagne. Les deux `publicKey: null` et les quatre autorisations sensibles à `false` font refuser le brouillon par le validateur actuel. Aucun succès de validation complète de spec n’est revendiqué.

Les fichiers `*.admission.proposed.json` conservent les propositions initiales exactes. Ils sont sémantiquement identiques aux admissions émises par Root, mais leurs octets et hashes diffèrent par sérialisation. La spec référence **uniquement les fichiers émis par Root**, jamais les hashes de ces brouillons. Le sourceMF commun, `d30e9e5c108974b84d0ab61452b48ef5a924dd4ab2d01877d8021b54006f4f1c` / 23604 octets, reste sans référence à ces admissions ni à la future spec.

## Temps et capacité à approuver

Clock proposée exactement depuis les trois valeurs historiques fournies par Root : startup `0x1d4c0` (120 s), downtime `0x927c0` (600 s), steps `0x8`. Ce sont des valeurs proposées, pas une qualification nouvelle. L’export frais entre dans la branche CLI qui fixe maximumForwardStepMs à 120 s ; huit steps couvrent donc au plus 960 s, tandis que la borne globale de 600 s reste plus stricte. Il faut `now >= durable >= genesis`, âge depuis genesis et durable <=600 s, ceil(âge durable/step)<=8 et ceil(step/slot)<=replaySlots. Les contrôles sont refaits avant chacun des trois premiers spawns, après attentes peer/tunnel/config ; ils ne sont pas réutilisés pour les restaurations. Aucun timestamp/genesis/profile n’est réécrit pour passer. Les 172742 ms d’un ancien composant ne garantissent pas le délai de la prochaine préparation complète.
