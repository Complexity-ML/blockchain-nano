# Worker Perl RPC EIP-1898

Source uniquement ; aucun Perl, compilateur, programme, conteneur ou SDK n’a été exécuté par l’auteur. Ce worker remplace le corps Python du contrôleur ROOT `062861a2…/17640`, après le refus réel de son premier démarrage : l’image ARM `e30ce85e…` ne contient pas Python. Cet échec reste conservé et ne constitue pas un échec C++ : aucune commande M, CXX ou test n’avait démarré.

ROOT monte ce fichier connu en `/controls/worker.pl` et appelle `/usr/bin/perl /controls/worker.pl`, sans argument supplémentaire. Les deux contrôles restent `/controls/recipes.json` (`coreFlags`, `testFlags`, `linkTail`) et `/controls/source-expected.private.json` (path guest physique → SHA-256/taille). Le worker exige un `/outputs` Linux neuf, vide, `0700`, appartenant à `501:20` ; les sources et anciens artefacts restent montés en lecture seule sous `/work`, `/baseline` et `/old`. ROOT conserve la responsabilité des pins hôte originaux, de l’image immuable, de la projection lisible, des premières admissions stabilisées et du nettoyage Docker. Ce fichier ne crée aucun conteneur, volume ou réseau.

Les outils guest employés sont `/usr/bin/clang++`, `/usr/bin/ar`, `/usr/bin/ranlib`, `/usr/bin/cp` et `/usr/bin/stat`. Les modules Perl sont fournis par Perl core : JSON::PP, Digest::SHA, Text::ParseWords, Fcntl, POSIX, Time::HiRes, Cwd, IO::Handle et IO::Select. Aucun paquet n’est installé. ROOT doit vérifier réellement leur disponibilité avant cette qualification ; la revue source n’en tient pas lieu.

Chaque commande projet utilise fork/exec sans shell, un répertoire de travail absolu `/outputs`, un groupe de processus neuf, des argv et journaux privés exclusifs, une borne de 180 secondes incluant le nettoyage et 16 Mio par flux. Un échec, une interruption ou un groupe descendant restant provoque TERM/KILL/join du seul groupe possédé. Le worker garde une borne globale de 590 secondes dans le contrôle externe de 600 secondes. Les captures GNU-stat sont également bornées. Les diagnostics stdout publics ne contiennent pas de chemins privés ou d’exceptions brutes.

Les neuf champs sont ceux du helper public `known-files.pl` : dev, ino, mode, nlink, uid, gid, taille, mtime, ctime. Ils restent des chaînes issues de GNU stat, sans atime et sans conversion de timestamps Perl arrondis. Les enregistrements privés portent `{material:[neuf chaînes], bytes, sha256}` : c’est un nouveau namespace Linux, pas une récupération ou normalisation des anciennes autorités Python/hôte. Chaque lecture contrôle l’identité FD/path et les neuf champs avant et après le hash. Les données projet doivent égaler les octets attendus ROOT ; les autres dépendances sont bornées au namespace de l’image immuable. Trois observations complètes égales pendant au moins deux secondes précèdent chaque CXX ; tout ancien matériau déjà tenu reste strict, sans refresh.

Le travail conserve deux TUs seulement (`test_rpc_simulation_block_id.cpp`, `rpc.cpp`), un vrai M indépendant et un MD de compilation égal, puis copie le Core et remplace seulement `rpc.cpp.o`. Les 142 autres membres restent byte-identiques et en ordre sur 143 ; le nouveau membre égale l’objet compilé. L’ancien Core est lié au test neuf et doit refuser exactement le premier objet canonique après sa baseline chaîne valide (`checks:4`, stage `canonical-selectors`, sortie 1 et message exact). Le candidat doit produire cinq scénarios, les compteurs cumulés 0/45/51/55/58, puis le résumé 5 groupes/58 refus. Aucun ancien test RPC, nœud ou serveur HTTP n’est lancé.

Les noms et le schéma de `result-public.json` restent ceux du contrôleur précédent ; seuls ses valeurs, temps et empreintes seront produits par le vrai essai ROOT. Les événements argv/exit, les MD, les snapshots et les résultats restent dans le volume neuf, puis leur transport borné en lecture seule relève de ROOT. Le worker évite aussi de lire `/outputs/libnano_core.a` avant sa création : le premier lien sélectionne exclusivement `/baseline/libnano_core.a`.

Cette source ne qualifie pas EIP-1898 dans son ensemble, une branche non canonique conservée, HTTP, un SDK global, la causalité complète du build, les duties, la finalité ou la production. La compilation, les refus et les compteurs sont encore attendus ; aucun résultat n’est inventé.
