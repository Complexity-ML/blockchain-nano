# Simulation RPC : sélecteurs de bloc qualifiés sur ARM

ROOT a réellement qualifié le nouveau sélecteur objet d’eth_call et l’extension correspondante d’eth_estimateGas dans Docker ARM, avec l’image existante. Le worker Docker termine avec le code 0 en 48 461 ms. Le parseur et la vérification de canonicalité sont partagés avec eth_createAccessList. L’[EIP-1898 primaire](https://eips.ethereum.org/EIPS/eip-1898) cite eth_call, sans citer estimateGas : sa prise en charge ici est une extension Nano explicite, pas une conformité globale à cet EIP.

Deux TUs seulement ont été compilés : `src/rpc.cpp` et le nouveau `tests/test_rpc_simulation_block_id.cpp`. Leurs vrais M indépendants égalent les MD, avec respectivement 529 et 463 dépendances ; ces nombres sont des ensembles distincts, pas un audit SDK global. Le Core est copié : sur 143 membres, les 142 autres restent inchangés et le membre rpc égale l’objet nouvellement compilé. Aucune image, ancien Core ou suite RPC complète n’est reconstruit ou rejoué.

La causalité est établie par deux liens du même nouveau test. Avec l’ancien Core, la première requête objet connue échoue exactement au stage canonical-selectors après une baseline chaîne réussie : code 1 attendu, quatre checks et zéro refus déjà compté. Avec le candidat, le sélecteur dédié passe cinq groupes, 120 checks et 58 refus attendus en 51 ms. Il couvre les sélecteurs canoniques hash/numéro, les objets malformés, les ressources inconnues, le contexte détaché conservé pendant un rewind, les hashes devenus obsolètes, l’annulation/échéance et l’état historique absent. Pending, les anciens sélecteurs chaînes et les codes de createAccessList sont préservés.

La tentative 01 reste un échec de préparation conservé byte pour byte : arrêt à container-interpreter-start avant M/CXX/test, trois contrôles nouvellement créés avec dérive de ctime seulement, octets identiques. La cause physique de cette dérive n’est pas établie. Les sources et manifestes des propositions restent également les copies exactes antérieures à la qualification ; leurs champs pending ou attentes ne remplacent pas les trois reçus réels de la tentative 02.

Le conteneur possédé est absent ; le volume Linux de sortie, le Core candidat et le test y sont conservés. Les racines de build originales étaient montées en lecture seule. La dernière fence confirme les neuf champs et SHA des 26 fichiers hôte retenus, sans refresh d’autorité. Aucun nœud, serveur HTTP, réseau ou duty n’a été démarré. Les soldes et bases de test sont synthétiques, sans clé ni signature de transaction nécessaire.

Le code ajoute une cible et un CTest dédiés, mais aucun configure CMake complet n’a été exécuté pour ce lot : la qualification fine utilise les recettes déjà retenues. CMake complet, candidat multiarchitecture et déploiement restent ouverts. Le Store ne fournit pas l’état propre d’une branche non canonique retenue ; un état indisponible est refusé sans substitution par l’état canonique de même hauteur. Ce cas, les autres méthodes EIP-1898, HTTP, AMD64, la CI, les admissions de campagne, les duties, la finalité commune et la production restent non qualifiés. Aucun fork ou EIP global n’est promu ; le goal reste actif.

Les trois sources du projet sont intégrées directement aux chemins consignés dans le manifeste : rpc.cpp, le nouveau test et CMakeLists.txt. Ce paquet ne duplique pas les gros fichiers rpc/CMake. Il conserve les petits reçus publics, le manifeste et le README de la proposition, ainsi que le worker Perl et le contrôleur hôte effectivement exécutés. Aucun fichier privé, SDK, binaire ou log brut n’est inclus. Les quatre documents conservent leur corps historique intégral, y compris l’append antérieur sur l’environnement natif.
