# Capella catalog page yielding — 30 September 2026

Previously one peer catalog could hold its relay permit across all pages until completion or the existing 30-second deadline. This change releases the authenticated snapshot after a page with exported/acknowledged payloads, returning delivery-page-yield rather than claiming a complete inventory. The existing peer scheduler then rotates categories. Admitted-root knowledge remains peer-session scoped. All-known pages may continue scanning; scan capacity, pacing, delivery acknowledgements, timeout, rejection and unknown-outcome rules remain unchanged. Runtime enables yielding only where acknowledgedRoots >= maximumEntries; smaller configured caches retain full-scan behavior. This avoids obvious insufficient-cache restart loops for a bounded stable inventory; it is not a general guarantee under arbitrary inventory churn.

Four new mocked-transport scenarios cover resumption across three catalogs without retransmission, entirely cached pages, rejected delivery and absent ACK. All 39 relay scenarios pass on Docker ARM64 and Docker VPS amd64; nano-p2p compiles on both. These tests do not prove consensus admission, network improvement or the cause of campaign C recovery delay. Runtime images and native P2P still need refreshing before the next bounded network qualification. No clock or finality rule was changed.
