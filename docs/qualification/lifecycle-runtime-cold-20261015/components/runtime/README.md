# Fresh lifecycle runtime integration — source candidate

This proposal implements a new branch of the real three-owner launcher. It has not been executed, compiled, imported, or qualified by its author. The ordinary fresh recovery and partition bodies retain their existing flow. The current repository and its unavailable lifecycle guard have not been changed.

The candidate keeps `runtimeDriverEnabled:false` by default. This preserves the existing specific pre-seed/pre-output refusal. Enabling it in an externally SHA-approved ROOT SPEC also requires `privateVpsLifecycleTransferAuthorized:true`, and, for a selected action owner outside VPS, `crossOwnerEvidenceTransferAuthorized:true`. These flags represent the separate specific human approval; this proposal does not supply it. They are checked before seed/ledger inspection, export, output creation, SSH or Docker. No new human approval channel per phase is introduced.

The runtime admission adds `lifecycleSubmit` (`nano-capella-lifecycle-submit`) alongside `lifecycleTool` (`nano-capella-deposit-audit`) for each owner. Both binaries must be independently qualified and pinned in the existing ROOT owner admissions against the selected current core. The tool must implement observe V3: `expectedHead:null` is allowed only for non-signing sealed observation; action and terminal still require the exact three HEAD fields. The private P/W closure, public-domain, external-token and physical-copy guards remain mandatory. No C++ implementation, clock, consensus profile or image is modified here.

The externally approved SPEC must declare the two exact fresh public identities before this launcher’s single export. The authority creator must independently derive those public keys from the new reserved seed without signing or exporting the domain twice. This proposal neither guesses an index from an environment name nor implements that ROOT seed authority step. It never reads an old campaign seed or reuses an old namespace.

The branch performs the following actual operations when separately authorized and run by ROOT:

1. Check source/software admissions, export and import exactly one fresh domain, and start the three real runtimes. Require the initial common-finality window.
2. Consume only that domain’s `assets/deposit.json`, submit its exact raw transaction, and observe real registration and activation through a header-pinned single-validator endpoint. A generic 404 is retried as unavailable state, never converted into a fabricated absent validator.
3. Find a finalized proposal by the newly activated key. Clean-stop VPS, retain two complete independently pinned P/W captures, copy the entire stopped owner data and witness roots (all signer journals and peer identity), authenticate restored copies before any writer, restart on those physically independent roots, and require three common-finality advances and a new finalized proposal by that key.
4. Wait the unchanged profile’s actual tenure. For each of the disjoint exit/slashing identities, clean-stop its owner, authenticate complete P/W captures, construct separate private core copies, obtain the exact sealed HEAD from C++ observe, and prepare the action on those same copies. Only the C++ PREPARED SHA/bytes pin admits the canonical action file.
5. Construct the new submission plan from the already pinned domain/program authority and the authenticated action commitment. Hash the known canonical bytes **before** O_EXCL/fsync. Make a single bounded first material admission, then give that same hash to the managed child. The child alone receives the supervisor token, submits once, retains its actual completed accepted Job locally, and execs the pinned real P2P program. A lost/unknown Submit is never retried. Common finality and the exact finalized public SSZ operation commitment are then required.
6. Wait actual withdrawability and finalized payload entries for both identities. These are scheduling candidates only: a later residual sync reward may legitimately create another full sweep. A zero post-state balance is not required and is not used as a payout oracle. Perform the second complete VPS backup/restore, with a third explicitly owned active unslashed key supplying finalized proposals before and after it; then require the recovery finality window.
7. Clean-stop and capture all three owners. Transfer only expressly approved cross-owner action/Job artifacts into VPS, keep all VPS capsules/sessions/raw reports there, and run one complete owner-local terminal C++ replay on independent private core copies. Its exact accounting, accepted-action, withdrawal-index, restart-proposal and finalized-ancestry checks are compulsory. Three stopped captures do not mean three terminal replays. Recheck both original backup sources, all admitted controls, software, historical HELD inputs, new outputs and cleanup before a final qualified flag can become true.

Long registration, tenure and withdrawal waits retain a rolling authenticated common-finality checkpoint. Before reaching the existing 1,024-block HTTP ancestry limit, the same three-owner observer must complete three real advances and three stable samples under a unique phase name. The refresh interval and deadline reserve derive from the newly pinned profile. A missed or impossible window refuses; HEAD roots never become baseline authority and the 1,024 bound is not raised. Terminal evidence converts the observer’s decimal epoch to the C++ canonical hexadecimal quantity only at that boundary. All action/REQUEST/plan admissions remain fenced through closing.

All phase waits and children have finite limits. The whole timer is `maximumRunMs`, checked independently of the actual profile-derived epoch horizon. Under the current public 8-slot/6-second example the earliest withdrawal bound is activation +325 epochs (15,600 seconds), plus registration/activation, finality, actions, two restores and audits. These values are derived from the new pinned profile; they are not a changed profile or a wall-clock success promise. ROOT’s outer wrapper must use that declared whole timer plus a separately bounded cleanup grace, not the former short campaign timer.

The two restore copies reuse the reviewed Linux FD/SHA scanner with an explicit owner-root target derivation and declared inventory ceilings. The original two-core-copy helper remains byte-identical. The source-only final fence intentionally checks only frozen original roots after resumed independent destinations start writing; it never claims resumed copies remained unchanged. Each copy and both complete captures are checked before the corresponding first resumed writer. Same-UID concurrent writer resistance is not claimed.

New checks are `lifecycle-runtime.test.mjs` (7 tests, 55 explicit refusal assertions, opaque OS-temp files only; ROOT to execute once) and a successor of the unavailable-guard test (three real child refusals: default disabled, missing VPS authorization, missing cross-owner authorization). The original eight pure lifecycle tests are unchanged. None is a runtime, Docker bind, supervisor, HTTP, cryptographic replay or campaign substitute. Production readiness, original V37 recovery, NAS, real funds/public deployment, full validator lifecycle qualification, and the pending private VPS permission remain open. All previous campaign failures retain their original results.
