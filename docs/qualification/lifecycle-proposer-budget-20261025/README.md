Le calcul du cycle facture les attentes déclarées de registration/activation et d'horizon, **10F +4P +2R +2A +3U**, avec R restauration, A action et U audit canonique. Les deux restaurations Mac ajoutent **2×(R+F+2P)** et la finalité initiale ajoute **F**. La réserve de clôture reste comprise dans le maximum global et ne finance pas les duties. Le format v1 garde P=F ; v2 exige P et un profil de planification explicitement épinglés, sans choisir de nouveaux paramètres de consensus. Le budget restant réel, l'historique, les octets d'archive/index et l'horizon sont contrôlés avant export puis avant les premiers lancements ; un profil exporté divergent est refusé.

Les vrais callers transmettent une échéance absolue unique, bornée par la phase et la fin du travail global, puis la revérifient après les attentes. L'identité choisie et le floor de journal restent fixes ; un résultat tardif, au-delà de l'horizon ou d'une capacité déclarée est refusé. P n'est pas une garantie qu'un validateur proposera effectivement un bloc.

Les deux exécutions utilisent l'image existante, Node 18.19.1 et Python 3.12.3, avec réseau Docker `none` et init. Chacune ferme ses **237 FD explicitement suivis**, sans échec secondaire ni stderr. Le reçu 02 atteste les fences strictes des fichiers suivis ; le reçu 01 conserve `runtimeAndSourceFilesStrictlyFenced:false` après son échec. Aucun build d'image, clé, exporter ou runtime de chaîne n'est lancé par ces tests. Cela n'établit pas une fermeture globale des runtimes Node/Python, ni une qualification du système de fichiers Mac.
