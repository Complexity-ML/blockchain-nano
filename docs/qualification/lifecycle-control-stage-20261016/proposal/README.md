# Lifecycle control staging and stopped-owner receipts

SOURCE proposal only. No Node, Perl, C++, tests, Docker, SSH, Git operations, SDK/private reads, campaign, signing, or R writes were performed by the author. Root executes the targeted qualification separately. The failed second campaign remains failed; these changes do not complete its lifecycle.

The public run source stages all five `manifest.files` from `remoteRoot/config`, including `genesis-state.ssz` and `genesis-validators.ssz`. The previous initial USTAR carried four public JSON documents, private node configuration and the existing owner-scoped environment only. Root reported that both SSZ files were absent remotely. This proposal adds the two **public** SSZ buffers only when the explicit lifecycle transport option is true. The ordinary six-file transport remains the default. Lifecycle transport validates the exact five manifest paths, SHA-256 and byte lengths against the buffers that are actually archived. This build step runs before runtime launch, registration and activation waits. It does not send public SSZ through argv, add any private key or change the 33-key VPS environment. Existing USTAR, file, reader and source-fence bounds remain unchanged.

`lifecycleControl` still stages the same six public documents (domain manifest plus five manifest files), private node configuration, then the independently held stop receipt. The remote Python stage program, C++ tool and protocol are unchanged. This is a transport/preflight correction, not a new authority for the public domain or a replacement for the previous native evidence.

A successful intermediate stop already removes its owner from `started`. If staging then fails before resume, the previous finalizer visited only the other two running owners and refused the three-receipt check before any terminal capture. The new pure `createLifecycleStopReceipts` tracker retains a cloned healthy stop receipt with its owner and exact logical roots plus backing mount description. Every lifecycle resume attempt invalidates that owner's receipt as its **first** operation, before asynchronous configuration or a new writer. A changed root binding without a resume also refuses. Only after the actual stop and receipt validation succeeds is `started` cleared. The lifecycle finalizer stops the remaining owners, collects all retained current receipts, and uses the existing three-capture/publication-before-closing path. Legacy non-lifecycle collection is unchanged.

Each actual `lifecycleCapture` now awaits persistence of its validated public projection to `<prefix>-capture-commitment-public.json` before returning to any staging, copying or resume step. The file contains only the existing allowlisted owner/storage/counter/flag projection and stop/first-capture/last-capture SHA-256 and byte commitments. It exports neither the remote capsule nor private paths, inventory, session or keys. Publication failure prevents the next step. The three-owner aggregate is still published before closing. This preserves future capture commitments when a later stage fails; it does **not** recover the missing independently retained second-stop pin of the already failed second campaign.

The tracker does not invent or replay a stop, infer process absence from a receipt, capture an old receipt against restored roots, repair a failed capture, or make an incomplete closure pass. Runtime process joins, actual owner captures, external stop/witness pins, final fences and the existing `lifecycleClosing` validation still apply. The first campaign error remains the first failure even when the public capture-only receipt is persisted. It still states `lifecycleTerminalQualified:false` and `productionQualified:false` until a separate actual terminal C++ result qualifies the lifecycle.
